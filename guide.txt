  1. What You Are Building
  A user uploads a video. The app extracts frames and audio, runs them through trained
  detection models, and returns a Fake Score from 0 to 100 plus an explanation (which
  frames looked suspicious, confidence, and so on). Around this core you build a normal
  SaaS product: landing page, pricing, login, dashboard, admin panel.

  Important honesty note: deepfake detection is an arms race. No detector is 100%
  accurate, and models trained on old datasets often fail on new generators (Sora-style,
  Veo, Kling, etc.). Always present the result as a probability, never as proof. Plan to retrain
  regularly.

  2. Core Concepts in Plain English
         Model: a program that learned patterns from examples. Here it learns what real vs
         fake videos look like.
         Dataset: a large collection of labeled examples (video + label real/fake).
         Training: showing the model many examples so it adjusts itself to tell them apart.
         Fine-tuning: starting from a model someone already trained and teaching it your
         specific task. This is what you will do. It is far cheaper than training from zero.
         Inference: using the trained model to score a new video.
         Metrics: accuracy, precision, recall, F1, AUC. For detection, AUC and recall on fake
         videos matter most.
         LLM vs classifier: you said "train an LLM", but for deepfake detection you mostly
         need vision models (image/video classifiers), not a chat LLM. An LLM (open-source,
         like Llama or Qwen) is useful later for explaining results and for the fake-information
         (text) detector.

  7.3 How to use OpenCode properly
  OpenCode works best when you give it small, clear tasks and a rules file.

     1. Create AGENTS.md in the repo root describing the stack, folder structure, coding
         style, and rule: "Make small changes, run tests after each change, never delete files
         without asking."
     2. Give one task per prompt, for example: "Create the Prisma schema for users, roles,
        videos, and analysis results."
     3. After each task: run the app, read the diff, commit to Git. Never accept huge changes
         blindly.
     4. When something breaks, paste the exact error and ask for a fix.
     5. Free models are weaker than top paid ones, so keep tasks small and review
        everything, especially security code (login, permissions).

  12. Phase 6: Detection Model: Pretrained First, Train Later
  (Beginner Friendly)
  This is the part you know nothing about, so go slowly.


  12.0 Fast Path: Start With a Pretrained Hugging Face Model
  Start with a model someone else already trained. Build and finish the whole app around it,
  then fine-tune your own model later only if the results are not good enough. Sections 12.1
  to 12.7 describe that later training step.

  How Hugging Face works here:

         A model is just files (weights plus a small config), usually a few hundred MB.
         The first run of from_pretrained("model-id") or pipeline(...) downloads them
         to ~/.cache/huggingface . After that everything runs on your own machine, even
         offline (set HF_HUB_OFFLINE=1 in production).
         No token is needed for public models. A token is needed only for gated models
         (accept the license on the model page), private repos, and uploading your own model.
         Do not use the hosted Inference API for real user videos: frames would be uploaded to
         a third party, which is a privacy problem and conflicts with the self-hosted goal.

  Steps:

     1. Search the Hub for "deepfake detection" and "AI-generated image detection".
        Shortlist two or three image-classification models.

     2. Check each model card: license (commercial use allowed?), training data, which fakes
         it was trained on, and the file format. Prefer safetensors files from reputable
         authors; old pickle-based files can run code when loaded.
     3. Run face detection first (MediaPipe or RetinaFace), then pass each face crop to the
         model.
     4. Build a benchmark of about 100 videos: real ones, compressed ones (WhatsApp,
        TikTok style), and fakes you generate with open-source tools.
     5. Compare the shortlisted models on the benchmark. Keep the best, or average the
        best two (an ensemble). Do not trust the accuracy claimed on the model card.
     6. Combine frame scores into the video score (section 12.6) and calibrate on your
         benchmark.

     from transformers import pipeline


     detector = pipeline("image-classification", model="MODEL_ID_FROM_HUB",
     device=-1) # -1 = CPU
     result = detector("face_crop.jpg")                     # e.g. [{'label': 'fake', 'score': 0.93},
     ...]


  Limits to expect: image models judge each frame alone, so they miss flicker and lip-sync
  problems, and they often fail on fakes from newer generators. That is the main reason to
  fine-tune later.


  12.1 Choose the approach
  Video deepfake detection usually works in two stages:

     1. Face and frame analysis: extract frames (for example 1 to 5 per second), detect and
        crop faces, classify each as real or fake with an image model.
     2. Temporal analysis: look at how things change across frames (flicker, unnatural
        blinking, lip sync mismatch). Aggregate frame scores, or use a video model.

  Start simple: frame-level classifier + average of top scores. Improve later.

         DFDC (Facebook/Meta Deepfake Detection Challenge, very large)

  This matters more than any single dataset.


  12.3 Prepare the data
     1. Download datasets into training/data/raw .
     2. Write a script to extract frames with FFmpeg or OpenCV.
     3. Detect and crop faces (open-source: MediaPipe, RetinaFace, or YOLO-face).
     4. Save crops into folders labeled real/ and fake/ .
     5. Split by video, not by frame: 70% train, 15% validation, 15% test. Frames from the
         same video must never appear in two splits, or your accuracy will look fake-good (data
         leakage).
     6. Balance classes (similar number of real and fake) or use class weights.
     7. Apply augmentation: compression, blur, brightness, resize. Real-world videos are
        compressed (WhatsApp, TikTok), and models that never saw compression fail badly.


  12.4 Pick a starting model (all open source)
         EfficientNet-B4 (classic and strong for deepfakes, light enough)
         Xception (used in FaceForensics++ benchmarks)
         Vision Transformer (ViT) / DINOv2 / CLIP backbones: modern, generalize better to
         unseen fakes
         VideoMAE or TimeSformer for true video models (heavier)

  Recommended first choice: fine-tune a CLIP or DINOv2 ViT backbone with a small
  classification head, because research shows these generalize better to new fake types
  than older CNNs. Keep EfficientNet-B4 as a fast baseline.

  12.5 Training steps (what actually happens)
  Do this step only if the pretrained model is not accurate enough on your benchmark. Run
  it on Kaggle or Colab, not on your laptop (2 GB VRAM is too small). Save the result as
   safetensors files, download them, and score locally. You can also push them to a private
  Hugging Face repo and download from there.

     1. Create a Python virtual environment, install torch , torchvision , transformers ,
          timm , opencv-python , scikit-learn , mlflow .
     2. Write a PyTorch Dataset that loads a face crop and its label.
     3. Load the pretrained model, replace the last layer with 2 outputs (real, fake).
     4. Settings to begin with: learning rate 1e-4 (head) / 1e-5 (backbone), batch size 32 (lower
         if GPU memory errors), 10 to 20 epochs, AdamW optimizer, cross-entropy loss, mixed
         precision (fp16) to save memory.
     5. After every epoch, evaluate on the validation set. Save the best model.
     6. Log everything in MLflow: loss curves, AUC, settings.
     7. Test once on the held-out test set at the end.
     8. Cross-dataset test: train on FaceForensics++, test on Celeb-DF. If accuracy collapses,
         you are overfitting. Add more varied data and augmentation.

  OpenCode can write all these scripts. Prompt it with: "Write a PyTorch training script that
  fine-tunes a timm EfficientNet-B4 on folders train/real and train/fake, with validation
  AUC, mixed precision, and MLflow logging."


  12.6 Turning model output into the 0 to 100 score
         The model outputs a probability that each frame is fake.
         Video score = weighted combination: mean of the top 30% most suspicious frames,
         blended with the temporal and audio scores.
         Calibrate the score (temperature scaling or isotonic regression on validation data) so
         that "80" really means roughly 80% of such videos are fake.
         Verdict bands: 0 to 30 likely real, 30 to 70 uncertain, 70 to 100 likely fake. Tune using
         validation results.


  12.7 Audio and lip-sync (phase 2 of the model)
  Add later: open-source audio anti-spoofing models (AASIST, wav2vec2-based detectors)
  and lip-sync mismatch detection (SyncNet). Combine with the visual score using a small
  fusion model.

  12.8 Where does an LLM fit?
  Use an open-source LLM (Qwen, Llama, Mistral) served locally with Ollama or vLLM to:

         Turn technical results into a human-readable explanation for the report.

  13. Phase 7: ML Inference Service (Python)
  A FastAPI app with this pipeline:

     1. Receive job (video path, job id) from the queue.
     2. Download video from MinIO.
     3. Validate with FFprobe (duration, codec, resolution).
     4. Extract frames and faces.
     5. Run the model in batches on GPU.
     6. Compute per-frame scores, temporal score, final score.
     7. Generate heatmaps (Grad-CAM) showing which face regions looked fake.
     8. Save results to the database and mark job done.
     9. Delete temporary files.

  Endpoints: GET /health , POST /analyze , GET /models . Keep it private (not exposed to
  the internet); only the Node API calls it.

  Performance tips: process one frame every 0.5 s, cap video length at first (for example 2
  minutes), use ONNX Runtime or TensorRT later to speed up.

  Make the model swappable. This lets you replace the pretrained model with your own
  later without touching the rest of the app:

         Put the model behind one class ( ModelBackend ) with one function,
          predict(frames) , that returns scores. The queue, database and result page never
         know which model is behind it.
         Keep the model id or local path in .env (for example MODEL_ID ), not in code.
         Save the model name and version in the modelVersion field of every Analysis row.
         Scores from different models are not comparable.

  16. Phase 10: Security (Very Important for This Product)
  As a cybersecurity professional, treat this as a security product from day one.

         Uploaded videos are untrusted input. Process them in an isolated container with no
         internet access, limited CPU/memory, and timeouts. Malicious media files can exploit
         decoders like FFmpeg, so keep it updated.
         Validate and limit uploads, use random storage names, and virus-scan with ClamAV.
         OWASP Top 10 checklist: injection, broken access control, XSS, CSRF, SSRF, insecure
         deserialization.
         Security headers (CSP, HSTS), HTTPS everywhere, secrets in a vault or encrypted env.
         Rate limiting and abuse protection on all endpoints.

         Encrypt data at rest, define retention (auto-delete videos after N days), and support
         user deletion.
         Audit logs for admin actions.
         Dependency scanning: Trivy, npm audit , pip-audit , Dependabot.
         Protect against adversarial attacks: attackers can modify fake videos to fool the
         detector. Test with compression, noise, and re-encoding; retrain on failures.

  22. Future Phases

  vector database like Qdrant or pgvector), have an open-source LLM compare claim and

  FakeNewsNet. Always show sources so users can verify.

  23. Common Beginner Mistakes
         Splitting data by frame instead of by video (fake high accuracy).
         Training only on one dataset and claiming general accuracy.
         Ignoring video compression in training data.
         Skipping calibration, so scores are meaningless.
         Letting OpenCode write huge changes without review.
         Exposing the ML service or storage publicly.
         Forgetting dataset licenses.
         Overpromising accuracy in marketing.
